● I wrote the guide to /home/ddergham/TAP/best-git-convention.md and linked it
  from step 7 of your plan.

  One correction to your request: you wrote -ff, but to get the graph you want,
  the merge has to be --no-ff.
  - --ff (fast-forward): your feature's commits go straight onto main as one
    flat line, and the branch disappears from the graph.
  - --no-ff: Git always creates a merge commit, so each feature shows up as its
    own loop in the graph. Section 7 of the guide has an example.

  If you really did mean a flat history, tell me and I'll change it.

  What's in the guide:
  - Five rules: never commit on main, one branch per feature, small commits,
    merge with --no-ff, delete the branch after merging.
  - One-time setup: your Git name and email, a setting so git pull never creates
    surprise merges, a .gitignore, and the GitHub setting that leaves only
    "Allow merge commits" on.
  - Naming: branches look like feat/gui-login or fix/take-race, and commits like
    feat(gui): add login screen, with good and bad examples.
  - An 8-step loop for every feature: start from main, create the branch,
    commit, push, catch up with main, get a review, merge, delete.
  - Help when stuck: what to do on a conflict, and a one-page cheat sheet with a
    checklist to run before every merge.
  - Branch list: your 14 plan steps, each with its branch name and example
    commits.

  One choice I made: before merging, you replay your branch on top of the latest
  main (git rebase). That keeps the graph tidy, but it's only safe on a branch
  nobody else is pushing to. The guide says this at the step itself.
